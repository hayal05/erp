# Phase 6: Departments, Positions and Default Salary  (est. ~700 LOC incl. tests)

Format: **Read** = reference to open first · **Open** = files to create/edit · **Done when** = acceptance check.
Requested by the owner on 2026-10-29, scope confirmed the same day. **Planning only: no application code is changed by this file.**

## The change in one paragraph
Add a dedicated **Departments** item to the HR sidebar. It lists departments with an **Add department** button. Opening a department shows a **Positions and salary** table: each position has a basic salary and **one allowance** (with its taxable and pensionable flags) and a pension flag. When HR creates an employee, or **changes an employee's position**, the employee's salary is **filled in from the position by default**. After saving, HR can still edit that employee's salary through the existing **Salary** button for exceptional cases.

## Owner answers (2026-10-29)
1. **No automatic move of existing employees onto positions.** The owner will do it manually. No backfill, no tool. Existing employees keep their job title and salary untouched.
2. **A position change applies the new position's salary by default**, and the salary stays editable after saving. See decision 5.
3. **One allowance** (decided after first considering several). Payroll already supports exactly one, so **payroll code does not change in this phase**.
4. **Confirmed:** a manual salary edit on an employee is an exception **for that person only**. It never changes the position or anyone else, and editing a position never changes people already on it.

## What exists today (checked in the code)
- `departments` table (id, name) and a complete HR API at `backend/src/routes/departments.js`. **There is no page for it**: HR cannot add a department from the UI today.
- Employees have `department_id` and a free-text `job_title`. There is no positions table.
- `salary_profiles` holds one row per employee: `basic_minor`, `allowance_minor`, `allowance_taxable`, `allowance_pensionable`, `pension_applies`. It is saved by `PUT /api/salary-profiles/:id` (`routes/salaryProfiles.js`, validation in `services/salaryProfiles.js`) and edited in `SalaryProfileDialog.jsx`. Nothing creates a profile when an employee is created.
- Approved and paid payrolls are immutable (database triggers). A salary change affects **draft** payrolls only.
- Sidebar is `HR_NAV` in `frontend/src/components/hrNav.js`, pinned to 7 items by `frontend/tests/hrNav.test.js` and spec §4.
- Money is integer minor units; `frontend/src/pages/salaryProfileForm.js` converts display units.

## Design decisions (agreed defaults; change before building if you disagree)
1. **Positions.** New `positions` table: `department_id` (FK, RESTRICT), `name`, and the **same five salary columns as `salary_profiles`** with the same limits. Unique on (department, lower(name)). Because the columns match, a position's package copies straight into a salary profile with no translation.
2. **`employees.position_id`** (nullable FK, RESTRICT). Employees without a position keep working as today. When a position is chosen the server writes its name into `job_title`, so payslips, CSV and the dashboard keep working with no new joins.
3. **Payroll is not touched.** Engine, `payroll_entries`, salary sheet, CSV, payslip and snapshots stay exactly as they are. The only payroll-adjacent change is that employee creation and position change now write the same `salary_profiles` row HR already edits by hand.
4. **Create applies the position.** Choosing a position copies its salary package into the new employee's profile **inside the same transaction as the employee insert**; if either fails, both roll back. The form shows a read-only preview; the server ignores any salary figures sent with the create request.
5. **Position change applies the new package by default, visibly and reversibly.** When HR changes an employee's position, the form shows the current salary next to the new position's salary and a checkbox **"Apply new position salary"**, **checked by default**. Unchecking it keeps the current salary (the exceptional case). The server replaces the salary only when the request says so, and audits before and after (same `payroll.profile.update` action, marked as coming from the position).
6. **Editing a position never changes existing employees.** A position is a template copied at assignment time. Changing a position's allowance does not touch anyone already assigned. **Confirmed by the owner 2026-10-29.** A per-person salary edit is likewise personal to that employee.
7. **Guards:** a position used by any employee returns 409 on delete; a department that still has positions returns 409 ("delete or move its positions first"); the position must belong to the employee's department (422 otherwise); changing department without choosing a valid position clears the position.
8. **Sidebar becomes 8 items**, Departments right after Employees; routes `/hr/departments` and `/hr/departments/:id`. Spec §4 and `hrNav.test.js` are updated on purpose.
9. **HR only**, `noStore`, audited: `position.create/update/delete`, existing `department.*`, `employee.create/update` details gain `positionId` and a salary-applied flag.
10. **Additive database change only** (new table, nullable column). No rewrite of existing rows.
